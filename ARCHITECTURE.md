# Architecture

The active PWA lives in `web/`; see [PWA architecture and validation](docs/PWA_VALIDATION.md). React/Vite serves the browser UI. Each user owns a Cloudflare Worker and SQLite Durable Object storing only encrypted API credentials, hashed sessions, cooldowns and bounded verification/cache receipts. Grade snapshots/history/scenarios remain in versioned IndexedDB. Same-origin APIs stage complete parsed snapshots before activation, sign only allowlisted Schoology GETs and validate redirects/pagination. A static-only service worker offers controlled updates. GitHub template-first setup copies the canonical root update launcher; Cloudflare connects that existing repository. Signed source releases update it through its own GitHub Actions at midnight America/New_York; its Cloudflare Builds performs deployment. The launcher remains a fixed permission boundary while signed runtime scripts evolve. Profile separately compares official releases and deployed app-shell versions, with explicit per-tab activation. See [automatic updates](docs/AUTOMATIC_UPDATES.md) for recovery, preview channels and actual verification limits. The following description is the preserved native reference, not the PWA security/storage model.

## Native reference

GradeViewer is one native local SwiftUI iPhone app, using Apple frameworks and the local GradeCore package. Schoology is its sole provider. There is no server, analytics, advertising, Muse dependency, widget, extension, App Group, or background polling.

`SchoologyProvider` → GradeCore source courses/calculations → stable canonical courses → protected SwiftData cache → SwiftUI.

## Identity and presentation

ProviderID has only Schoology. Section/grade-owner/period and typed assignment IDs define identities; titles never deduplicate two different assignments. The latest fetched repeated source ID wins. Reconciler preserves existing canonical course IDs, order, visibility, and history, retains known titles when fresh metadata is missing, and replaces data only after a complete successful snapshot. A schema-valid empty snapshot removes the previous Schoology records; failure preserves them.

Course/Assignment keep their serialized source arrays for cache compatibility, but each active entity has one Schoology source. AssignmentGrouping reads that source’s categories directly. Recent lists filter ungraded rows; All Assignments also includes named rows without scores, while excluding unnamed empty placeholders. Graded rows order real score updates descending, then due date, title and identity. Rows without scores do not claim a grade-update date. An ungraded catalog item never becomes an additional score. Hypothetical edits/additions contribute exactly once through GradeCalculator.

GradingPeriods interprets Schoology's explicit quarter/semester/exam ranges and weights. One home card appears per physical grade-owner section. Quarter districts retain Q1–Q4 assignment pills; semester-only districts use their actual periods. Exams appear read-only under their uniquely containing dated quarter and never enter that quarter's calculation. Home and a selected quarter’s detail summary use the same uniquely containing semester. Calendar-date boundaries include the full final local school day; explicit timestamps keep their exact instant. Semester freshness uses its real component score dates. Unknown dates are never invented.

## Totals, scenarios, and charts

Reported numeric/letter Schoology totals are authoritative. If no interpretable numeric/letter total is available, SchoologyGrades uses the canonical calculator and the normal Course Grade label. Schoology hides category methods and drop counts from student accounts; omitted methods retain the pre-migration points default and omitted drop counts retain zero. Provenance records these defaults, which are not proof of the teacher's hidden rules. Explicit unsupported category methods, missing weighting mode/points or letter-only assignment contributions leave the calculation unavailable. JSON null/blank totals are omitted values. Section `grading_scales` metadata verifies nonzero numeric/percent overall scales before their reported totals are used. Unsupported/ambiguous/hidden numeric scales remain uninterpretable. An uninterpretable overall custom-scale value is never treated as a percentage and does not block a separate calculation from numeric assignment points. A reported letter is never converted to a made-up percentage.

A missing semester total may be calculated from explicitly associated available quarters/exams and their declared weights, normalized for the in-progress total. An included graded component lacking a usable total/weight prevents that calculation. A quarter scenario affects a semester only when the component baseline reproduces its total within 0.15 percentage point. Local editing applies only the scenario delta to a reproducible basis. Edit/drop/reset/Add Grade behavior and local scenario labels remain unchanged; calculation-specific badges are removed at the user's request. No provider writes exist.

The user-authorized `PeriodGradeEstimate` is presentation-only inverse math: `unknown = (semester × sum(active weights) − sum(known grade × weight)) / unknown weight`. It requires a reported semester and other-quarter total, a unique dated two-quarter semester, known nonnegative component weights, a positive unknown weight and named target assignments. Reported exam totals contribute at their weight; a blank exam contributes neither grade nor weight, disclosed beside the asterisk. Zero is a real exam score. A second unresolved contribution, visible override, unsupported scale, overlapping dates/semesters, negative result, or an indistinguishable known-only total withholds the estimate. A conservative one-hundredth budget for each reported input propagates as `0.01 × (active total weight + known component weight) / missing weight`. Estimated presentation uses at most one decimal when this is below 0.05 point, whole percentages below 0.5 point, and withholds a less stable result. Raw inverse arithmetic stays full precision; the UI discloses rounded-input limits. This budget is not proof of provider rounding/hidden rules, and unreported overrides remain a limitation. No student-specific scores/weights are embedded. Fresh actual totals/scores take priority without a stored estimate to clear; date rollover selects the new quarter and triggers the existing open/foreground refresh, but does not fabricate provider availability. Estimates never enter history, raw source grades, assignment points or scenario baselines.

Optional `Course.removedAssignmentIDs` stores explicit local removals by provider identity, survives reconciliation and decodes older caches. Presentation and the canonical calculation source omit those rows; raw source arrays and reported totals remain intact. Restore is reversible. Removed identities skip optional title recovery, including expired negative-cache retries, while full fresh grades are still read. There is no rule that silently removes every inaccessible or untitled graded row.

ScenarioRecord holds score overrides, dropped rows and added grades. Add Grade opens a direct name/score/total popup, with a category choice only when needed. Added rows are first in Recent and grouped in All Assignments; edit/drop/remove/reset stay local. ScoreInput preserves finite decimal precision and supports existing signed/extra-credit values without clamping. The final calculator uses the user-entered syllabus weight.

Reported changes of at least 0.01 percentage point (with a 1e-9 binary-comparison epsilon), letter changes and source transitions create observed history. Calculated totals/prefixes never enter observed history. The course graph spans the section's available assignment periods, using quarters when present or the district's actual semester/named periods. Each period uses its own canonical calculation; semester rollups/exams are not duplicated as quarter contributions. A first connection halfway through the year reconstructs earlier progression from the complete Schoology grades already fetched, using real score-update/due dates only when that period's complete baseline is reliable. A single dated score also supplies a point. No first-install date is imposed as a history cutoff.

Saved observations remain unchanged. Completed periods contribute observations made by their end date and dated assignment prefixes; fetching a completed quarter today does not move its endpoint to today. Only the latest populated assignment period contributes a calculated current point at its actual snapshot fetch time. This keeps the endpoint correct after imported observations, even without assignment dates. Schoology exposes current scores and their latest update timestamps, not every earlier score revision: a new install cannot recover overwritten grades or missing dates. Reconstruction is not a provider audit log. Equal timestamps have stable ordering; actual observations override calculated events at an identical timestamp. Reconstructed prefixes within one hundredth of an observation in the same assignment interval adopt that observation for presentation only. Anchors never cross a period or the next assignment event, alter saved observations/scores/dates, or apply today’s offset to earlier prefixes. Actual current calculated endpoints stay separate. Real observed 0.01 changes and small changes at new assignment events remain visible. The tooltip shows only the selected event's grade/date, never interpolated values/dates.

## Refresh and Schoology security

Startup loads saved data synchronously, then requests fresh Schoology grades. Grades remain covered until Schoology commits a fresh snapshot; Profile/retry stay reachable. Launch, real background return, pull/Retry and active-only minute checks coalesce one in-flight read. Temporary inactivity does not trigger a new read. Schoology is the only refresh dependency.

Every refresh verifies users/me against the credential-bound account. Fresh enrollments and complete combined grades are read concurrently; verified enrollment/grade-owner aliases avoid repeated per-section reads. Section reads have bounded concurrency. If an optional scale request fails, recent already-verified scale types may be reused for the same account/section/scale for at most one hour, retaining their original verification time; ambiguous/expired metadata is rejected. Optional scale/title reads follow required data, use validated typed/wrapper IDs, preserve scores on unavailable metadata, and defer on throttling. Complete unchanged metadata may be reused for five minutes; period metadata expires after an hour, with original non-sliding timestamps. New rules require a new metadata version, preventing pre-upgrade metadata from skipping the first rule-validation read. Manual refresh and grade changes bypass the short cache. Manual title retries bypass local negative lookups but honor server cooldowns. Metadata schema version 7 invalidates earlier parser/scale/boundary assumptions.

Schoology OAuth 1.0 credentials stay in installation-scoped Keychain using WhenUnlockedThisDeviceOnly. CryptoKit supplies HMAC-SHA1. URLSession is ephemeral, GET-only, HTTPS/origin/path restricted, without cookie storage or a disk response cache. Redirects are freshly signed and pagination is validated. Short 429 delays get one bounded retry after the shared server deadline. Longer/repeated waits resume at the deadline while active; no early requests or background polls occur. Failures preserve saved grades and credentials.

Connection activation saves pending credentials before verification, preserves active credentials/data if serialization or persistence fails, and clears the pending attempt only after a successful commit. Disconnect removes Schoology data/history/scenarios. Disconnect before switching accounts; unexpected Schoology owner changes are rejected before student reads.

Protected debug diagnostics contain only fixed labels, structural field types/counts, booleans and timings. Ordinary refreshes do not collect them. Credentials, response values, identifiers and student grades are never logged.

## Existing-installation upgrade

SchoologyUpgrade reads the legacy JSON archive without retaining any retired provider enum, parser, transport, cookie or browser implementation. It selects Schoology source records, keeps canonical course identity/order/visibility and unchanged historical observations with their original opaque origin labels, and remaps unambiguous edit/drop identities. Unique matching/catalog evidence may preserve previously resolved assignment titles. Added grades move to the Schoology identity and uniquely compatible category. Ambiguous archived overrides are retained but not applied to unrelated rows.

GradeRepository prepares/serializes all upgraded payloads before one differential SwiftData transaction, rolling back on any failure. The old MappingRecord entity remains only for SwiftData schema compatibility; its records are cleared during upgrade and there is no mapping API/UI. Reopening is idempotent. Retired Keychain connection/pending items are deleted only after the saved cache opens successfully; the Schoology Keychain items remain intact. Local migration tests use disposable stores. An authorized installation upgrades the existing phone store through this same transaction; protected read-only captures verify preservation.

## Signing and validation

Config/Signing.xcconfig uses neutral defaults and includes ignored Signing.local.xcconfig. Keep the same installation team/bundle ID to preserve its Keychain/data. New clones use their own identities/accounts. No team/district is hardcoded. Edit project.yml and regenerate the committed Xcode project for target/build changes.

Core tests run with swift test. Hosted tests use in-memory SwiftData/disposable Keychain items, and XCTest drives simulator UI from CLI with ad-hoc signing. Fixtures are synthetic. Captured-account comparison/migration checks export only aggregate counts/booleans. See PROJECT_STATUS.md and docs/PROVIDER_PARITY_AUDIT.md for actual results and limits. Original-phone installation and post-install evidence are recorded in PROJECT_STATUS.md; another account/district remains unverified.
