# Architecture

## Runtime

GradeViewer is one native SwiftUI iPhone application. There is no GradeViewer server, analytics, advertising SDK, cloud account, or required external watcher. The only package is the local GradeCore Swift package, built from the same repository. Apple frameworks handle networking, OAuth cryptography, persistence, credentials, and charts.

`SchoologyProvider` / `InfiniteCampusProvider` → typed source courses → `Reconciler` → canonical `Course` / `Assignment` → SwiftData cache → SwiftUI.

## Canonical model

`Term`, `GradingCategory`, `Score`, `OverallGrade`, `SourceCourse`, `SourceAssignment`, `Provenance`, `Course`, `Assignment`, `GradeHistorySnapshot`, and `Hypothesis` live in GradeCore. Source identity includes provider, section, term, task/item kind, and provider ID. Two providers' raw IDs are never interchangeable. A course has one or more complete source records; an assignment has one or more source variants. Selected original fields and IDs remain in provenance for debugging; full student payloads are not written to logs.

Course identity includes term/task. Campus standards/tasks never get averaged together or collapsed into a single annual grade. Task identity remains separate internally. Normal course headings use the original course name without task/quarter suffixes. The current term is selected internally from provider dates, with available grades as a fallback; the home list contains one current card per physical section. Quarter-only pills appear in View All Assignments when provider quarters exist; semester-only or explicitly dated named-period districts use their actual periods. Equivalent quarter labels are recognized on the home list, and known disjoint dates cannot share a selected term merely because both are named Q1. Semester and exam records remain internal; their grades are presented within the quarter view.

## Matching and display

1. Auto-match only a mutual unique pair across providers whose evidenced periods also agree on one physical section pair. An ambiguous or conflicting physical section cannot partially merge through a unique quarter. Exact normalized title/term/teacher metadata remains sufficient. Missing teacher or different term labels can instead use the same title words and at least two shared assignment title/points identities that each occur once in each source, or matching explicit period kind and start/end boundaries. Placeholders do not count. The latter works before a class has any scores. Conflicting nonempty teachers and disjoint known term ranges reject a match. Normalization folds case, diacritics, punctuation, and whitespace. Ambiguous candidates remain separate.
2. Previously saved explicit mappings remain compatible with the cache, but cannot override known teacher/date/kind conflicts. Manual matching, hiding and ordering screens are removed from Settings; current-term selection and automatic matching handle presentation. No source rows are deleted simply because their titles repeat.
3. Within a matched course, assignments match only when a real title, UTC due-calendar day, and known finite nonnegative points possible agree, and there is exactly one candidate from each provider. Missing dates and ambiguous repeated titles remain separate. Metadata without timezone is currently parsed as UTC; district timezone calibration is still required during live validation.
4. Campus supplies the displayed overall grade when available; otherwise a source with a grade is selected. An actual zero is available data. For assignments, a scored/excused Campus variant wins, with a scored Schoology variant as fallback. All variants remain stored, even on disagreement.
5. A source disagreement can be inspected from the course or assignment detail. The normal list contains no provider diagnostics.
6. On a new source joining an existing canonical entity, retain its identity, history, order, and visibility. When a merged entity splits after metadata changes, only one split inherits the old identity; regression tests cover both courses and assignments.

The scoring basis is always one complete provider's source course, normally the displayed Campus course. Reconciled assignments from both providers are for presentation; they are never summed twice in a calculator.

## Grading period hierarchy

GradingPeriods is the canonical period interpretation in GradeCore. It distinguishes quarters, semesters, exams, annual totals, and unknown periods. Schoology section grading-period metadata supplies explicit dates/weights; dates embedded in provider period names are another explicit source. No missing date is fabricated. Campus task names distinguish Quarter, Exam, and Final even when they share Q2/Q4 term IDs.

Mutually unique evidenced period pairs establish a one-to-one physical Campus section ↔ Schoology grade-owner association. Only within that association can compatible empty quarters/exams/finals link by period kind and explicit ranges. Quarters require matching boundaries. Campus Final may inherit its closing quarter's range; it must share the semester's end and be contained in the explicit semester range. Exam ranges must overlap. Conflicting teachers, years, kinds, or duplicated candidate sections remain separate.

The home list selects one regular current grading task per physical section. All source periods/tasks remain cached. The class overview keeps the current quarter's graph and recent assignments. For quarter districts, View All Assignments has one equal-width capsule of quarter-only pills. A selected quarter shows only that quarter's assignments; Course Grade shows its associated semester's reported overall with an S1/S2 label. Semester/exam choices are absent from a quarter district's selector; a district with no quarter records can select its actual semesters or explicitly dated named periods. GradingPeriods.exams associates an exam only with its unique containing quarter by explicit dates, falling back to a shared same-provider term ID only when dates are unavailable. Known conflicting dates and ambiguous containers reject the association. Q2 shows the first-semester exam after its normal groups; a declared second-semester exam similarly appears under Q4. Exam rows are read-only and never become quarter calculator contributions. Pill selection is remembered separately from the current overview. When a semester association is unavailable, the selected period's reported grade remains visible.

A quarter What-If delta can affect the semester summary only when explicit component weights reproduce the reported semester overall within the existing 0.15-point reliability tolerance. Available components are normalized as the provider's current in-progress total requires. Unknown weights/rules do not produce a semester scenario. Whole-semester presentation rows outside a complete reliable source basis are read-only.

## Schoology categories and assignment presentation

AssignmentGrouping is separate from canonical reconciliation. It prefers an already-linked Schoology source; otherwise it requires compatible period kind/dates, the exact normalized course name, at least two matching assignment title/points pairs, and one unique Schoology grade owner. It must not borrow categories from ambiguous classes. Within that evidenced association, an unambiguous title/points pair can supply category metadata when provider due dates differ. This does not merge canonical course records or change the calculator source.

Schoology's optional assignmentCatalog retains grade-item metadata across periods, independently of period scores. Metadata without a score can classify a graded Campus row; it is never shown as a graded assignment or added to the calculator by itself. Already-scored Schoology item IDs suppress duplicate catalog metadata even without due dates.

The overview includes graded Campus rows plus distinct graded Schoology rows in the associated current period. It does not omit a real Schoology-only score just because Campus has not supplied it. Campus variants retain display priority when a row is linked. Normal full-assignment navigation respects the selected period. The internal semester presentation helper gathers only explicitly associated quarters/exam and deduplicates physical IDs; normal navigation exposes only quarter selection when quarters exist. The legacy fullCourse helper still supports the prior cache/fixture presentation across related tasks; it is not used to mix unrelated periods in the pill selector. Neither full-view history nor Schoology category association alters the current overall grade/calculation basis. Historical or Schoology-only rows outside that basis cannot edit the current Campus grade through a fabricated contribution.

Schoology metadata keys prefer the documented `grade_item_id` over a wrapper `id`, with type included in identity. Explicitly unique wrapper aliases are supported, and a newer unknown catalog kind can supply metadata only when its primary node ID and points/category/period evidence agree. Detail reads validate either the requested wrapper ID or graded-node ID and reject conflicting known kinds; original score identities remain intact. Missing graded assignment titles can use the documented enrolled-section assignment detail route, with bounded concurrency and exact returned-ID validation. Previously resolved titles are retained for the same source identity; unavailable optional metadata leaves a neutral Untitled assignment rather than a numeric ID. Metadata never supplies a grade. Schema-invalid collections or incomplete pagination reject the provider snapshot. Schoology count_in_grade exclusions are respected.

Course freshness uses the same overview association as the detail sheet and the latest graded timestamp across retained variants. Assignment rendering preserves reconciled title/date metadata when applying local score edits. Full assignments resolve their current course from the observable store rather than retaining an old navigation snapshot.

One AssignmentOrdering implementation serves overview and full groups: real score-update dates descending, undated rows after dated ones, then due date descending, normalized title ascending, and stable ID. Ungraded rows are excluded from visible lists; actual numeric zero and extra credit remain graded. Relative update labels round to the nearest hour/day and are static; they never schedule refreshes or substitute due/fetch dates for score updates.

## Persistence and startup

SwiftData uses its local SQLite store with CloudKit explicitly disabled. CourseRecord stores one canonical course payload, including its source records and history. ScenarioRecord stores local hypotheses. MappingRecord stores explicit provider matches. Differential saves insert, update, or delete individual records; they do not delete and rebuild the database. Saves roll back on error.

Startup synchronously loads the cache into an observable store, initializes the freshness gate, then starts an asynchronous refresh. Launch and actual background-to-foreground return request a refresh; temporary inactive/active transitions do not trigger an immediate refresh. A cancellable one-minute check remains only while active. Manual and foreground refresh callers join the same in-flight task. Provider snapshots fetch concurrently and publish independently as each completes; Campus details and Schoology grades/metadata use bounded concurrency, with four connections per host. Saved values remain internal until the foreground presentation gate opens. The opaque gate replaces grade content, including its accessibility tree, before the first rendered grade view and is reset when the scene backgrounds. Each connected provider must deliver fresh data after foreground entry. A failed provider keeps the saved snapshot but presents a retry/reconnect screen, rather than exposing old grades. Profile and sheet dismissal remain available; class/period selection lives in the observable store and survives the temporary gate; normal manual/active checks do not cover an already fresh view. URLSession and provider fetch/parsing run asynchronously; assignments use lazy scrolling. Read-only source snapshots are committed only after an entire provider refresh succeeds. Failed providers retain their previous data. A successful empty provider result removes only that provider's records. A malformed response must not be interpreted as an empty successful snapshot.

History records changes of at least 0.01 percentage point, a letter-grade change, or a display-provider change. Unchanged refreshes do not add snapshots. First observation begins stored history. The chart may additionally calculate score prefixes off the main thread, once per source update, using the canonical calculator only when the complete assignment baseline is reliable and scored rows have usable dates. These presentation-only points are never saved as actual snapshots. Each prefix is anchored to the reported baseline using `reported + prefixCalculation - completeCalculation`, the same basis as What-If. Its endpoint therefore equals the provider grade; a rounding offset cannot fabricate a final 0.01 transition. The user explicitly requested removing basis text from the tooltip: it now shows grade/date only. The reconstruction still uses current score prefixes, with actual score-update dates preferred over due dates; this is not a recovered audit log. Reconstruction now runs through the latest source fetch rather than stopping at the first app observation. Each assignment contributes one prefix point; equal score timestamps use due date then stable source identity for ordering, without fabricating times. A tied batch's intermediate prefixes are deterministic reconstruction, not proof those totals were separately published. An incomplete date set keeps the actual observed point. Demo history is synthetic and isolated.

## Authentication and transport

Every Schoology refresh first verifies `users/me` against the credential-bound identity, then uses the documented combined user-grade list plus previously verified owner/enrollment aliases, avoiding per-enrollment grade reads for empty sections. An unexpected identity change requires disconnect before student reads. Even a schema-valid empty initial snapshot retains its verified identity. First connections and unresolved new owners retain per-section resolution. Grade scores always come from fresh reads. Optional section period metadata is cached for one hour with its original fetch time; new period IDs force metadata renewal. The cache does not extend its own expiry on each grade refresh.

Schoology accepts personal OAuth 1.0 consumer key/secret, plus optional access-token/secret. Requests use CryptoKit HMAC-SHA1, as specified by OAuth 1.0. HMAC implementation is Apple's; a protocol test checks the RFC 5849 signature vector. Redirects, including `/users/me`, get a fresh nonce and signature. Pagination and redirects remain within the approved HTTPS origin/path. Schoology's documented HTTP pagination links are upgraded only for its own API host.

Campus opens the user's actual HTTPS Campus Student portal in a nonpersistent WKWebView. District lookup runs inside the same view and remembers the selected student portal before SSO navigation. Safari login sessions are separate; the app never tries to extract Safari cookies. No login-page scripts are injected and no password fields are read. Initial SSO sign-in remains user-driven. Connect obtains Campus-origin cookies plus IdP cookies scoped to hosts actually visited during SSO from WKHTTPCookieStore. A separate pending Keychain item is saved before verification so a failed setup can be retried manually; Connected and cached grades change only after a successful full fetch. Both older student login URLs and the observed modern nav-wrapper/student home derive the application base correctly. The grade transport receives only Campus cookies; a separate optional SSO value in the same Keychain item contains IdP cookies, their visited hosts, and a validated reusable same-origin Campus Student SSO entry. It contains no assertions or IdP redirect queries. Older items decode without that optional value. ASWebAuthenticationSession was considered; no public student OAuth/callback contract was found, and that API does not provide a general export of a website's Safari session cookies.

Credentials, Campus cookies and reusable SSO cookies are stored in app-scoped Keychain items using `WhenUnlockedThisDeviceOnly`. Campus passwords are never stored by GradeViewer. URLSession uses an ephemeral private cookie jar, HTTPS, same-origin reads, standard TLS validation, and no disk cache. Pending Schoology credentials follow the same manual retry/forget flow. Failed new setup leaves active credentials intact, including when a successful fetch cannot be serialized or saved locally. Pending setup material is cleared only after the snapshot commits. Successful reconnection clears stale rate-limit deadlines. Response cookies are persisted after every Campus fetch attempt, including failures after a rotation; expired/deleted cookies and non-Campus domains are excluded. A Campus-only connection retains the same-origin portal retry. With reusable IdP cookies, one authentication rejection instead starts the district’s normal SAML entry in a new memory-only WKWebView. Automatic navigation is limited to HTTPS Campus and previously visited IdP hosts, with a 20-second bound and cancellation/process-failure cleanup. After an IdP visit and Campus return, the complete fresh grade fetch verifies new Campus authorization; a particular Student-home URL is not required because a district may return to a shared Campus page. The saved validated Student URL remains the fallback. Cookie rotation is retained in Keychain. A finished sign-in requirement disables automatic renewal until interactive sign-in, preventing foreground/minute loops; network failures remain retryable. Expiration/rejection preserves cached grades. Interactive login restores both scoped cookie sets, handles normal SSO popups, and never reads/fills login fields. A 429 pauses further attempts until Retry-After. Schoology GETs share a cooldown and retry at most once for delays up to 30 seconds, retaining completed work during a short initial-fetch limit. Longer/repeated limits return to the app deadline; cancellation interrupts waits. No unbounded retry loop.

Campus requests explicitly set their Cookie header from Foundation's domain/path/expiry-filtered private jar, with automatic request cookie handling disabled. Response cookies continue to update that same jar before status handling; server deletions remove cookies even on HTTP 401. Fixtures check the transmitted header and a new client's restored/rotated cookies. The earlier masked Cookie-header import was removed from the app UI at the user’s request after SAML renewal was verified. GradeCore retains its strict standalone header parser and scope/injection tests; the normal user flow needs no cookie copying or cookie configuration. Settings contains only connections and Appearance. Healthy connection pages conceal setup fields; initial setup/explicit Schoology updates expose only the required personal key/secret or district URL. Disconnect lives on the provider page and retains its data-removal confirmation. SSO readiness, transport diagnostics, optional token controls, version boilerplate are hidden. Pending setup exposes concise retry/clear actions only when needed. Demo UI never loads active Campus credentials, and demo disconnect cannot delete real Keychain connections.

Connection setup and explicit debug diagnostics use fixed stage/error labels and an allowlist of JSON field names with types, never values. No URL, identifier, query, Authorization header, cookie, or raw error description is retained. Unknown field names are counted rather than copied. A bounded 200-entry structural/timing report is written to Library/Caches. Ordinary refreshes do not collect reports or do the additional schema parse. Explicit DEBUG --verify-layout and --profile-refresh CLI launches can collect the same protected report to verify live fixes; they add only counts/booleans, elapsed times, and fixed route labels.

The debug flags also collect Campus HTTP status and counts of eligible/session cookies, never cookie names, values, domains or dates. These distinguish absent local authentication from an HTTP 401 with restored cookies; neither a cookie count nor a portal HTML 200 proves an authenticated session or its lifetime. Safe SSO diagnostics add only readiness/attempt booleans, an IdP-cookie count and up to 50 fixed navigation-stage labels. DEBUG --verify-campus-renewal runs once per process with only IdP cookies in its fresh browser. A failed probe keeps the already verified active snapshot/session; normal provider failures retain the existing failure gate.

StoredCookie preserves provider-supplied HttpOnly alongside Secure, domain, path and expiry so a normal WebKit reconnect does not expose previously HttpOnly cookies to page scripts. SameSite is also preserved, and false Secure is restored by omitting that property (Foundation treats any supplied Secure value as true). Optional fields decode existing Keychain payloads without migration; absent legacy/imported flags cannot be inferred.

This app supports one student's own accounts. Disconnect before changing accounts; it removes that provider's data and resets local history/scenarios/mappings. Both live fetch pipelines and normal Dublin City sign-in succeeded on the student's phone. Schoology identity binding is checked locally; Campus account identity binding, expiry, and broader schema/rule coverage still need verification. Never silently mix students.

## Calculations

The calculator supports total points, weighted categories, equal category weights, points or average-percent category aggregation, assignment multipliers, category exclusions, excused/explicitly dropped items, ungraded exclusion, extra-credit numerator points, and dropping lowest scores. Empty weighted categories are omitted and active weights are renormalized. Intermediate values are not rounded.

Unsupported/missing rules do not generate a made-up number. What-If first checks that the complete visible source assignments reproduce the reported overall within 0.15 percentage point. If not, it gives a concise actual mismatch message. This is not evidence that the student's account contains hidden grades. The documented Campus portal visibility caveat is in RESEARCH.md. Rubric scales, district rounding/overrides, and advanced drop rules need live calibration before claiming parity.

No-op/stale score overrides are removed by Hypothesis.normalized(for:). A reliable hypothesis applies only its computed change to the reported provider grade: reported + scenario calculation − baseline calculation. The reported/calculated rounding offset therefore never becomes a fake blue +0.01% result. Blue course text and delta badges require a material local change.

Hypothetical edits, drops, restores, and resets in overview, assignment lists, categories, and What-If share the same ScenarioRecord. They never call a provider write endpoint. Real grades and grade history remain unaffected. The final calculator uses `(target - current × (1 - finalWeight)) / finalWeight`; the user enters the syllabus weight, and impossible/extra-credit targets are explicit.

## UI

Screens use restrained warm neutrals, native navigation/sheets/forms, clear grade alignment, and one original chart icon. System/light/dark appearance persists in UserDefaults. A flat Grades/Profile footer and rounded course cards follow the supplied references. The course sheet contains Course Grade, the progression chart, five recent assignment cards, and View All Assignments. Course tools are in the three-dot menu; assignment edit/drop/undrop/reset are in their own menus. All-assignment groups start collapsed, with Total Points for points-based courses. Graph events occupy equal horizontal intervals; timestamps provide labels rather than proportional x spacing. Hold/drag continuously samples the monotone cubic geometry for the marker only. The tooltip selects the nearest event and changes its two-decimal grade/date together at midpoint thresholds, never calculating a percentage or date between events. It retains the halo, full-contrast selected line and dim remainder. Single-point data draws a flat line. The tooltip contains no reconstruction label. Selection clears on finger release. The graph remains interactive in both appearances; its tooltip layers above the section heading. Screens omit promotions, subscription UI, decorative statistics, inspirational copy, alternate icons, and notification infrastructure.

The widget extension, WidgetKit imports, App Group entitlements, shared summaries, models, preview route, and URL scheme have been removed. No shared container or extension signing is required. App refreshes run on launch, real foreground return, manual pull, and once a minute while active. No background provider polling runs. Freshness labels reevaluate on those updates; checkmarks last less than 24 hours and ages over 30 days use completed 30-day months.

## Portable signing

`Config/Signing.xcconfig` provides neutral defaults and optionally includes the ignored root `Signing.local.xcconfig`. The app and test bundle IDs derive from `GRADEVIEWER_BUNDLE_ID`; no developer team is committed. The original checkout overrides both values locally to retain the installed bundle/Keychain scope. `SecureStore` uses the app's bundle identifier as its Keychain service, preserving the existing service when that identifier is unchanged and isolating custom clones. Never delete the original installation as part of an update. District SSO entries are captured from normal navigation or restored from the saved session; there is no district-specific fallback URL.

## Validation boundaries

Core tests run on macOS with `swift test`. Hosted iOS tests use disposable in-memory SwiftData and test Keychain items. XCTest drives the UI from CLI; no computer-use tools are used. HTTP tests use URLProtocol stubs, never real schools. Production provider success, district/session expiry, server latency, and rate-limit behavior cannot be inferred from fixtures. See PROJECT_STATUS.md for actual results.

## Measured refresh performance pass — October 1

Matching evidence (normalized names/teachers, period descriptors, shared assignment-label identities) is indexed once per immutable provider snapshot, rather than reconstructed for every source pair. Date parsers and constant period regexes are reused. Foundation ISO date formatters are protected by a lock across concurrent provider tasks; epochs retain their fast path. This indexing preserves the conservative matching rules described above and the existing calculator provenance.

Refresh and connection pipelines reconcile and JSON-encode Sendable snapshots in a user-initiated detached worker. SwiftData remains on its owning main context, applying changed payloads atomically. A revision check rebases an in-flight worker if a local order/visibility/mapping update occurred. Provider freshness is acknowledged only after successful persistence, so an encoding/storage failure cannot uncover old data.

Schoology stores its verified user identity beside the exact credential set in Keychain and rechecks it through users/me. Fresh enrollment and combined-grade reads then run concurrently. New/replaced credentials have no cached identity; every subsequent read still authenticates normally and 401/429 behavior remains intact. Optional title recovery uses exact unique compatible IDs from scoped assignment lists, then a bounded course-folder traversal (three concurrent reads, at most 32 folders, visited-set cycle protection, no response URL following). Failed title lookups have a 15-minute retry deadline, invalidated by score/timestamp changes; fresh grade-item titles always take priority. No grade score is cached by this deadline.

Scene changes arm a new automatic refresh only after actual background entry. Transient inactive/active transitions do not refresh or reset the gate. The existing active-minute check is preserved; its task cancels on inactivity/background. Automatic launch/return and manual pull remain. The gate covers an actual fresh-data entry until every connected provider has committed a fresh snapshot. An operation completing while backgrounded cannot uncover it.

`--profile-refresh` enables a debug-only protected timing/count report and bounded structural HTTP diagnostics, without running the expensive `--verify-layout` graph/report computations. Its 16-ms main-actor sleep probe measures scheduling lateness, not rendered FPS or all OS stalls. Normal launches collect neither HTTP shapes nor heartbeat data. See docs/PERFORMANCE_REPORT.md for measurements and reproducibility limits.
