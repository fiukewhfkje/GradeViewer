# Architecture

GradeViewer is a Schoology-primary React/TypeScript PWA with optional selected Infinite Campus courses. `web/` is the self-contained build, deployment and template root. The retired Swift app and its build/test infrastructure remain in Git history. `web/src/core/` owns current grade behavior; no Swift or macOS tooling is needed.

## Optional connectors and session maintenance

IC and experimental Carmen use independent, automatic HTTP session checks after successful sign-in at 20 and 90 minutes, respectively. The existing alarm dispatcher schedules both. IC maintenance never opens a browser, and neither maintenance task writes local grades or history. Each provider has a compact health indicator in Settings and a private sanitized diagnostic record. The operator capability is limited to the two diagnostic GETs. Exact session lifetimes and the effect on provider idle limits remain unverified.

Carmen shares PortalService's encrypted sessions, cookie jar, identity checks, browser restoration and request budgets with IC. IC imports selected courses. Carmen auto-discovers student courses, and its local main-LMS switch selects the visible courses, GPA and foreground refresh target while preserving both providers. A stable workspace identity permits Carmen without Schoology while preserving existing Schoology-first browser account keys. Confirmed authentication rejection alone permits bounded Carmen browser recovery when maintenance is enabled. Credentials, Duo, policies, cleanup failures and budgets stop it. Ohio State GPA settings and letter points are separate from Dublin's. An unlocked owner can copy a sanitized Carmen compatibility report from Settings. [Implementation and evidence limits](docs/CARMEN_INTEGRATION.md).

## Browser and Worker

React/Vite renders Grades, Settings, course details, assignments, local scenarios and the final calculator. Desktop uses a navigation/course sidebar, course grid and side-by-side panels; phone navigation remains compact. Held chart selection owns its touch gesture, tolerates vertical drift and follows display frames. `web/src/core/` provides framework-independent models, parsing, calculations, periods/estimates, reconciliation and progression. `refresh.ts` coordinates fresh reads; `repository.ts` stores versioned IndexedDB snapshots, observations, scenarios and metadata, with prepared-save recovery.

Each user owns a Cloudflare Worker and SQLite Durable Object. `web/worker/` stores encrypted API credentials, hashed owner sessions, cooldowns and bounded verification/cache receipts. Grade snapshots, history and scenarios remain in the browser. The original `APP_PASSWORD` binding seeds the login and derives the AES-GCM vault key. An in-app password change replaces the login verifier with salted PBKDF2, revokes other browser sessions and leaves the binding and encrypted connections intact. Cloudflare executes decryption and signing and is part of the trust boundary. An owner-set `APP_PASSWORD_RESET` secret can replace the login verifier once without changing the vault key.

Only fixed, enrolled-section Schoology GET routes are signed. Identity verification precedes student reads; redirects are re-signed and origin/path/pagination/payload limits are enforced. Pending credentials activate only after complete parsing and prepared browser persistence. Failure retains the prior connection and snapshot; switching students requires disconnect. No provider write endpoints exist.

## Grade identities and calculations

Section/grade-owner/period and typed assignment IDs define identity; titles never merge distinct assignments. Reconciliation preserves course identity, ordering, observations and explicit local removals. Only a complete schema-valid successful snapshot replaces saved data, including a valid empty result. Schoology enrollments without a gradebook row are omitted. Cached snapshots discard legacy metadata-only placeholders and reset obsolete `Course.hidden` flags while preserving grades, history, scenarios and GPA preferences. Explicit current visibility uses the separate account-bound browser `hiddenSchoology` physical-section keys. The canonical workspace selector excludes every hidden Schoology scope from the roster and GPA, retains independent IC/Carmen identities, and Settings restores a whole section. Refresh/prepared-save recovery, local edits and LMS switching preserve those preferences; account changes clear them. No provider data is deleted and hidden courses retain normal refresh verification.

Reported interpretable numeric/letter totals take priority. Verified numeric/percent scales permit numeric overall interpretation; unsupported or hidden scales do not become percentages. Omitted student-hidden category methods/drop counts retain points/zero defaults, with provenance rather than a claim about hidden teacher rules. Explicit unsupported rules, incomplete numeric contributions and letter-only assignments withhold unsupported calculations. Each assignment contributes once, including local editing, drops and additions.

Home and detail share the uniquely associated semester summary. Quarter scopes retain their own assignments/rules; exams appear read-only under the uniquely containing dated quarter and do not enter that quarter’s calculation. Date-only and timezone-free midnight boundaries cover the full local school day; explicitly zoned timestamps retain their exact instant. Semester scenarios require a reproducible baseline within 0.15 percentage point and apply only the local delta. The final calculator uses the entered syllabus weight.

A missing-quarter estimate inverses a reported semester using explicit, unambiguous component weights and known totals. Blank exams contribute neither grade nor weight; a reported zero is real. Unsupported scales, ambiguous dates/components, overrides or unstable propagated rounding uncertainty withhold the estimate. Estimates remain presentation-only, disclose their basis and never create assignment scores, observed history or scenario baselines. Actual reported/calculated totals take priority.

## Progression and refresh

IC normalization accepts task-level category weighting/score-percent options as well as consistent category declarations. Composite child weights remain relative ratios and are assigned only within the uniquely resolved same-section semester; incomplete or conflicting rules withhold reconstruction. Course graphs track the uniquely associated semester’s authoritative observations and current endpoint. Weighted historical quarter/exam events are reconstructed only when complete declared component weights reproduce the semester baseline; ambiguous association, missing inputs or overrides withhold reconstruction. Estimates never enter the graph or history. Separately calculated dated prefixes remain distinct from actual observations. Progression never invents dates or overwritten provider score revisions. Actual observations win at identical timestamps. Matching reconstruction may align within one hundredth only inside the same assignment interval; genuine small observed changes and new assignment events stay visible. Evenly spaced events and monotone interpolation supply geometry; tooltips contain the selected actual event’s grade/date only. The displayed window is the last 60 days; stored history remains intact. A single event is shown as a horizontal line with that event’s actual date.

Launch, actual hidden-to-visible foreground return and manual refresh coalesce in-flight reads. There is no recurring idle grade scan, duplicate visible events do not scan, and a Schoology cooldown permits one separate automatic retry after Retry-After plus five seconds. Its browser-local allowance is atomically claimed across tabs and survives reloads; another failure stops automatic attempts until success or an explicit manual attempt. It runs only while visible, online and unlocked, targets Schoology alone, and announces waiting/running/failure. A Schoology 429 still propagates without an inline retry. IC settings actions refresh only IC after the existing account/authentication checks; normal opens and manual grade refresh still refresh both providers. Previously unlocked browsers immediately restore an account-matched local snapshot using a local receipt bounded by the verified Worker session expiry, while server verification and fresh reads run silently. Provider failure retains those grades with an explicit saved-data notice and Retry. An unexpired previously unlocked browser can read its own cache offline. Explicit local Lock, expired receipts and account mismatches block restoration; a failed server logout cannot re-open the local cache. Provider/API access still requires the HttpOnly Worker session. Initial connections wait for complete verified data. Cross-tab refresh preserves open courses/forms and merges local edits into the new snapshot. Metadata/alias receipts have fixed expiry; manual refresh bypasses reuse while honoring server cooldowns. Returning automatic refreshes defer optional title traversal; required reads precede optional metadata recovery. The initial scan can return required first-page metadata and validate reuse receipts after fresh identity/discovery reads, saving one app round trip. Pagination, ambiguous aliases and older Workers retain the existing fallback. Both initial and later batches share the same canonical five-read scheduler; the initial invocation counts identity/roots and redirects against its 44-subrequest cap. Optional missing-title lookups honor their 15-minute failure backoff even on manual refresh; required catalogs still refresh fully. IC/Carmen detail reads refill three slots as they finish, stop queued work on failure and drain peers before retaining cookies. A peer 429 takes priority so its cooldown cannot be lost. Bounded batches enforce concurrency, subrequest and aggregate payload budgets. See [performance evidence](docs/PERFORMANCE_REPORT.md) for measurements and limits.

The authenticated `refresh/start` entry point combines status and the requested fresh snapshot work. It calls the same canonical scan-start implementation as older clients. A normal Schoology + IC refresh can overlap independent HTTP reads inside one serialized vault operation. A response-body-aware pool holds at most five slots globally, with the existing per-provider limits; IC's identity/summary/selected-detail allowance is reserved inside the 44-subrequest total. A 429 is recorded at response headers so queued requests for that provider stop before fetching, while the other provider can finish. Per-provider success/error envelopes preserve independent local commits and prevent an inline retry of a failed companion. No grade snapshot or plaintext credential cache is persisted on the Worker.

The browser checks local Lock, prepared-save recovery and queued-refresh coalescing before using that entry point. Automatic cooldown retries still verify status and atomically claim their allowance before any new provider work. Account mismatch returns status only. Unsupported older Workers retain the existing fallback, and a network failure never retries the combined request. IC/Carmen-only actions do not depend on Schoology metadata. Portal checks return their saved post-check health directly from the connection already in memory, avoiding another decrypt/status request. Schoology credentials are unsealed once per invocation and used only within that call; identity, enrollment and individual request signatures remain unchanged.

## Installation, updates and validation

The static-only service worker caches the app shell, never API responses. Controlled per-tab activation compares cached shell identity, waits for service-worker takeover and preserves browser-local data and open forms. Static `_headers` and API wrappers enforce security headers.

GitHub template-first setup copies the root updater launcher; Cloudflare connects that repository with root `web`. Signed source releases update each copy through GitHub Actions at midnight America/New_York; Cloudflare Builds deploys to its existing address. Exact official repository/workflow/tag/commit provenance and file hashes are verified before writes. Personal configuration, secrets and workflow permissions are preserved. Initial template copies may initialize a short root README; later owner edits remain untouched. See [automatic updates](docs/AUTOMATIC_UPDATES.md).

Build, unit/security/integration tests, synthetic Chromium/WebKit flows and release packaging use Node tooling from `web/`. Migration-only Swift comparisons were removed after their final 1,200-case pass; focused calculator regressions remain in `web/tests/core.test.ts`. Physical phone, independent-account setup and performance claims require their own evidence. See [current status](PROJECT_STATUS.md) and [validation](docs/PWA_VALIDATION.md).

## Optional Infinite Campus

`PortalService` shares the owner-authenticated Worker boundary and existing encryption, retaining browser/session cookies and a selected-course checklist in a separate encrypted record. Cloudflare Browser Run opens only when the user selects Connect or Reconnect, with cleanup on finish, cancel or the four-minute limit. Live View creation overlaps the initial navigation, and the sign-in window can open after navigation commits. IC refresh uses HTTP and marks the connection for reconnect if the saved session is rejected. HTTP grade reads use tough-cookie, fixed district paths, student binding, schema limits and selected sectionID details. Grades remain local. The TypeScript IC adapter supplies provider-scoped physical/assignment identities and reported-grade provenance. Provider refreshes retain one another’s snapshots on failures; no course linking or assignment merging exists. GPA reuses supported semester grades and groups compatible IC/Schoology semester windows without changing existing Schoology settings keys. Actual IC roster identity/schema and PWA SSO compatibility are not yet student-verified. Stable includes Experimental Carmen; enrolled-account parsing remains acceptance work.

## District discovery

IC sign-in opens the official Infinite Campus district finder in the temporary browser, like the historical native flow. Human navigation chooses the district and Campus Student. The canonical campus-url helper recognizes both legacy Student JSP and modern nav-wrapper home URLs, with Student-only paths and an HTTPS Campus host allowlist. Reusable destinations discard SAML/relay queries and fragments. During the temporary sign-in, a Durable Object alarm checks Browser Run page targets, including SSO popups. The Worker verifies the student identity and grades read before saving the encrypted session and closing Chrome. Settings checks the attempt status and shows the first-time course picker. The authenticated Student Profile can establish identity for a new connection when the schedule has no student ID. Grade reads remain same-origin and read-only. Reconnect restores the remembered district. No URL copying or native tooling is required.
