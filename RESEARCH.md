# Research notes

Researched September 29, 2026. Classifications: **documented** means published by the provider; **public client evidence** means visible source/client behavior; **tested locally** means fixtures or simulator; **student verified** means tested with this user's real authenticated account. Both complete authenticated grade fetches succeeded on the student's iPhone. The observations below are structural/status evidence; exact displayed values, session TTL, and change-feed semantics remain separate validation work.

## Infinite Campus: chosen path

Campus's [OneRoster API documentation](https://kb.infinitecampus.com/help/oneroster-api) describes access for third-party systems given integration credentials. It does not supply a public student OAuth grant. District/vendor integration is a different authority from the student's portal login. No district credential, paid integration, or GradeViewer backend is assumed.

The official [parent/student help](https://www.infinitecampus.com/support/parents-and-students) documents district-specific Campus Student login and the normal mobile Stay Logged In option. The [Campus Student Portal guide](https://kb.infinitecampus.com/help/campus-student-portal) describes current grade/assignment tools and recent score/grade updates. It does not publish a student JSON API contract, session TTL, or renewal token protocol.

Public source evidence supports trying these authenticated browser resources relative to the district's application base:

- `GET resources/portal/grades`
- `GET resources/portal/grades/detail/{sectionID}`
- `GET resources/portal/roster` (not needed by the initial app)

Sources: [Grades++ service worker](https://github.com/jonathanjma/Infinite-Campus/blob/main/extension/service_worker.js), [its detail parsing](https://github.com/jonathanjma/Infinite-Campus/blob/main/extension/pages/class.js), and [unofficial Node client](https://github.com/tonyzimbinski/infinite-campus/blob/master/index.js). GitHub reported last pushes January 16, 2024 and August 30, 2024 respectively. These are **historical public implementations**, not proof of compatibility with the user's 2026 district. The public Grades++ home page passes `course.sectionID` to its detail page, which requests `grades/detail/{sectionID}`. The first GradeViewer implementation incorrectly used `_id`; this misreading was identified after authenticated requests returned empty arrays. It has been corrected with a reproducing regression. [Home-page identifier source](https://github.com/jonathanjma/Infinite-Campus/blob/main/extension/pages/main.js). Original Swift parsing was written from observed field structure; no third-party implementation was copied.

License/reuse decision: Node client is GPL-3.0 and uses the deprecated `request` ecosystem; Grades++ has no declared license. Neither is a suitable dependency or source for copying into this native app. Their endpoints and field observations inform independent integration research. Apple's URLSession/WebKit are sufficient for the small read-only adapter.

The Node client's `verify.jsp` login sends credentials in a query string. It is deliberately **not implemented**. GradeViewer opens the exact student portal page; the student handles login/SSO normally, then the app stores only same-origin session cookies in Keychain. The public source also shows old `prism` notification reads, worth validating for Muse but not blindly using as a current contract.

Apple's [WKWebsiteDataStore documentation](https://developer.apple.com/documentation/webkit/wkwebsitedatastore) supports a nonpersistent store with WKHTTPCookieStore. [ASWebAuthenticationSession's documented workflow](https://developer.apple.com/documentation/authenticationservices/authenticating-a-user-through-a-web-service) requires a cooperating authentication callback. A normal Campus portal cookie session does not establish that callback. A district SSO provider may reject embedded views; actual user flow remains a validation gate.

## Documented calculation caveat

[Campus Portal Setup](https://kb.infinitecampus.com/help/portal-setup-admin) states that teachers can hide portal assignments/scores while including them in the calculation. This is a provider capability, **not an observation about this student's account**. GradeViewer never fabricates hidden assignment rows. The app only reports a calculation mismatch when its actual visible data cannot reproduce the reported grade. Unsupported grading rules are similarly evidence-based; source overall grades remain the display authority.

## Schoology

[Authentication documentation](https://developers.schoology.com/api-documentation/authentication/) describes OAuth 1.0 and personal two-legged keys, with an empty `oauth_token`, as well as three-legged token/secret credentials. The app supports both input formats, HMAC-SHA1 signing, and freshly signed `/users/me` redirects. No raw Schoology password is needed.

Read-only initial adapter endpoints:

| Endpoint relative to `https://api.schoology.com/v1/` | Purpose |
| --- | --- |
| `users/me` | Identify the authorized user |
| `users/{id}/sections` | Enrolled sections, following pagination |
| `sections/{id}` | Course title and grading configuration |
| `users/{id}/grades?section_id={section}` | Student grades, period totals |
| `sections/{id}/grade_items` | Assignment/discussion/assessment metadata |
| `sections/{id}/grading_categories` | Category methods, weights, drop count |

Sources: [User](https://developers.schoology.com/api-documentation/rest-api-v1/user/), [Course Section](https://developers.schoology.com/api-documentation/rest-api-v1/course-section/), [Grade](https://developers.schoology.com/api-documentation/rest-api-v1/grade/), [Assignment](https://developers.schoology.com/api-documentation/rest-api-v1/assignment/), [Grading Categories](https://developer.schoology.com/api-documentation/rest-api-v1/grading-categories/). The student's keys successfully accessed user identity, enrolled sections, student grades, enrolled-section metadata, grade items, and categories. A grades response returned an alternate grade-owner section ID; its direct grade-items request returned 403. The adapter therefore retains the enrolled ID for accessible metadata and uses the returned owner only for canonical grade identity, accepting an alternate owner only in an unambiguous single-section response. Missing optional metadata is not silently interpreted as complete grading rules. The initial app uses full successful provider snapshots on launch/manual refresh; incremental watcher logic is separate.

The grades documentation offers a `timestamp` changed-since query. [Event Triggers](https://developers.schoology.com/api-documentation/rest-api-triggers-v1/) requires school admin Trigger UI access. [Receiving Event Objects](https://developers.schoology.com/api-documentation/rest-api-triggers-v1/event_objects/) includes grades-save events, making webhooks preferable **if** a district grants the needed access. Student credentials alone do not establish that authority. [Reminders](https://developers.schoology.com/api-documentation/rest-api-v1/reminders/) is not documented as a complete grade-change log.

[PowerSchool system requirements](https://uc.powerschool-docs.com/en/schoology/latest/system-requirements) publishes a default bucket of 50 public API credits, refilled every five seconds; GET costs one, and exhausted requests return 429/Retry-After. This is a published default, not observed throughput for this account. Campus student-portal limits were not found. See MUSE_WATCHER_REPORT.md for responsible request estimates and verification gates.

## Follow-up ordering and missing Biology row

The user's side-by-side screenshots showed a recent Biology extra-credit row in Bessy and absent from GradeViewer. A narrow debug-only phone report confirmed that exact reference row exists in the associated Schoology grade snapshot and is absent from Campus's snapshot. It was not an ungraded row, and there was no numeric Campus score silently lost by the parser. The overview previously used only canonical current-course rows; it now includes distinct graded Schoology rows through the evidenced class association. The reference row is second after correction. All five current classes were inspected for source coverage and ordering. Exact score-date ties previously had no explicit secondary sort, and unknown score dates were mixed with due dates. A single deterministic rule now sorts real score dates descending, places undated scores last, then uses due date, normalized title and stable ID. The original timestamp labels truncated elapsed units; nearest-unit rounding matches the supplied hour-boundary examples without altering source timestamps or introducing a timer.

Bessy's [FAQ](https://www.bessy.io/faq) documents full assignments and three-dot edit/drop/category actions but does not publish sorting tie-breakers, normalization, or rounding code. Its algorithm has not been recovered. The user's screenshots support descending recent-score chronology; the tie-break rule is GradeViewer's explicit implementation choice, not a claim about private Bessy code.

PowerSchool's [Infinite Campus implementation guide](https://uc.powerschool-docs.com/en/schoology/latest/infinite-campus-implementation-and-configuration-guide) describes district-configured grade passback and separate data authorities. That documents why sources can legitimately differ in general; it does not establish which district sync job produced this specific missing row. GradeViewer only reads and preserves source differences.

## Explicit periods and final title recovery — October 1

The new Physics screenshots demonstrate Campus Q1/Q2 Quarter tasks and Q2 Exam/Final tasks, while Schoology nests Q1, Q2, and Exam under S1. Schoology’s official [course-section API](https://developers.schoology.com/api-documentation/rest-api-v1/course-section/) documents the section-specific grading_periods read with IDs, titles, weights, start, and end. This is the student section route, not the separate administrator-only district grading-period API. The canonical model now uses that explicit metadata, as well as dates actually supplied in period titles, to associate semester totals and component periods. Unique matching boundaries support ungraded classes; existing evidenced physical pairs support empty terms/tasks. No absent date or grade is invented.

Protected phone reports verified one home card for each of five classes and a matched semester for all five. Each class retained four quarter records, two semester records, an exam, and an overall record. These are this account’s observed record counts, not a claim that every district exposes the same hierarchy. Previous-quarter selection and semester-wide presentation are exercised with synthetic scores; naturally populated completed previous-quarter data still needs district observation.

The catalog supplied six Biology titles, but their grade rows referred to wrapper IDs while detail responses supplied another grade_item_id. Exact requested wrapper-ID validation fixes those joins without changing scores. A subsequent installed build had zero untitled Biology rows. One other assignment detail returned HTTP 403; its score is retained with a neutral title. Provider metadata access is not fabricated.

A live hardening run returned HTTP 429 with Retry-After 10 seconds, so request volume is a demonstrated concern. Repeat refreshes now use the documented combined [user-grade read](https://developers.schoology.com/api-documentation/rest-api-v1/grade/) with previously verified enrollment aliases, falling back to per-section resolution for new/unresolved owners. Explicit period metadata has a one-hour cache that keeps its original expiry and renews on new period IDs. Actual grades still refresh every time. After normal Campus reconnection, both providers succeeded across reinstall/relaunch; one completed run measured roughly 0.84 seconds for Campus and 5.37 seconds for Schoology. These are single-run measurements; resolved title reuse and metadata caching reduce subsequent work, and server response times remain external.

The user’s latest presentation preference supersedes cache-first display: saved data is retained internally, but foreground grade views show a loading gate until every connected provider supplies fresh data. Failures offer retry/reconnect instead of flashing saved grades. The checkmark remains 24 hours after the user’s correction; ages beyond 30 days show completed 30-day months.

The user rejected the separate period-selection screen after seeing it on the phone, then removed semester/exam views too. View All Assignments now offers only quarter pills. Exam grades and graded assignments appear below their uniquely associated quarter: Q2 for the demonstrated first-semester exam, or Q4 for a declared second-semester exam. Explicit unique date containment, or the same provider's shared Quarter/Exam term ID when dates are unavailable, determines this presentation association. Known conflicting dates and ambiguous containers reject the association. Exam rows are read-only; the quarter's calculator stays unchanged. The class overview keeps the current quarter and its semester overall.

## October 1 performance and inaccessible-title evidence

The phone profiler reproduced 4.51/4.59-second main-thread reconciliation windows during one 10.401-second refresh. Schoology parsing itself was only 21–87 ms per section in that run, and HTTP reads were generally 100–400 ms. The dominant problem was rebuilding period/name/date evidence inside pairwise reconciliation, blocking the main actor and delaying publication/provider completions. Local indices and worker normalization/encoding remove that work from the UI thread. Exact protected measurements and caveats are in docs/PERFORMANCE_REPORT.md.

The [User Grades API](https://developers.schoology.com/api-documentation/rest-api-v1/user-grades/) documents the combined user-grade list; it is distinct from the section-grade API. Enrollment discovery and that list can be read independently after identity is verified. The optional verified identity is stored with its credential set in Keychain; no fresh grade request is skipped.

The [Assignment API](https://developers.schoology.com/api-documentation/rest-api-v1/assignment/) documents scoped assignment lists and node/wrapper identities. [Course Folder](https://developers.schoology.com/api-documentation/rest-api-v1/course-folder/) documents root folder 0 and explicit content IDs/titles. Those provide conservative fallback metadata paths after inaccessible detail reads. On this phone, one detail repeatedly returned 403 with no response body; neither its 26-row assignment list nor all 16 reachable folders supplied that identity/title. The grade owner and enrollment were identical for that item, so the previously corrected alias mismatch does not explain it. A specific teacher setting/deletion/API defect is not established. Its valid score is retained, and repeated unsuccessful optional reads back off; the provider denial itself cannot be overridden locally. Synthetic tests demonstrate successful list/folder recovery, conflicting identity/kind/points/category/period rejection, cycles, retry expiry, authentication, and throttling.

Apple's [DateFormatter documentation](https://developer.apple.com/documentation/foundation/dateformatter) informs the reused configured formatter design; a lock also protects ISO8601DateFormatter, which is not Sendable. [ScenePhase](https://developer.apple.com/documentation/swiftui/scenephase) represents active/inactive/background state. The final user preference keeps actual foreground return refreshing; temporary inactive transitions are ignored.
