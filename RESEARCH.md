# Schoology research

GradeViewer supports Schoology only. The active application is the PWA; native source remains the reference for grade behavior and UI. Current deployment and validation evidence is in [PWA validation](docs/PWA_VALIDATION.md). Original-account observations below do not establish access or behavior for every school.

## Verified grade behavior — October 15, 2026

**Documented:** [User Grades](https://developers.schoology.com/api-documentation/rest-api-v1/user-grades/) separates assignment rows by `period_id` and returns `final_grade` records with grades/weights; period filters are available. [Course Section](https://developers.schoology.com/api-documentation/rest-api-v1/course-section/) exposes category weighting mode, category weights and scale metadata. [Midterms and finals](https://uc.powerschool-docs.com/en/schoology/latest/midterms-and-finals) explains that an exam can be weighted against a parent’s sub-periods or against overall periods. These are different levels of weighting, not interchangeable fields.

**Original-account verification:** fresh reads return category weights and quarter/exam weights. All five home totals now retain directly reported semester values after numeric/percent scales are verified. A nonzero scale ID did not mean the value was uninterpretable; that was a GradeViewer interpretation bug. Column `grade_item_id: 0`, typed external-tool wrapper IDs and JSON-null points exposed three further client parsing bugs. Compatible catalog identities now recover metadata without changing earned scores or accepting conflicting points/category/period/kind evidence. All graded Biology titles resolve. The [section endpoint](https://developers.schoology.com/api-documentation/rest-api-v1/course-section/) documents `start`/`end` with timezone-free midnight strings, while the [grading-period contract](https://developers.schoology.com/api-documentation/rest-api-v1/grading-period/) defines calendar dates. Both date-only and that midnight encoding retain whole local days; explicit zoned instants remain exact. Whole-day date handling also reproduced the premature term switch and old history-based freshness labels; local inclusive calendar days and component freshness correct those client bugs.

**Physics evidence and limit:** complete bulk, section-specific and period-filtered assignment reads return no numeric Q2 scores for the screenshot’s graded work. The directly reported semester total nevertheless matches the weighted result including that work. The underlying reason for the individual-score omission is unknown; hiding future-period grades until their start is a student hypothesis, not verified provider policy. The next foreground/open read will use whatever the API actually returns, without assuming a date unlocks it.

**Requested temporary estimate:** GradeCore inverses the reported weighted average to obtain a missing quarter total, displayed with an asterisk. The captured Physics data reproduces the student screenshot under this equation. Blank exams are excluded from the normalized average; a reported exam grade, including zero, participates at its declared weight. That blank-exam assumption is disclosed; rounded inputs/unreported overrides can affect the estimate. Fixtures verify unequal/non-100 weights, scored/blank/zero/zero-weight exams, extra credit, invalid/ambiguous inputs and replacement by actual scores. This does not recover individual assignment scores or establish a universal provider calculation contract. No estimate enters observed history or calculator inputs.

**CSA evidence:** the full screenshot’s 30 rows all match (28 graded, two without scores). The API has one additional untitled graded Homework row: its detail is inaccessible and complete lists/all 16 reachable folders do not resolve it. This establishes an extra API row relative to the screenshot, not an accidental-creation/deletion cause. The real Weekly Programs row is present and retained. At the user’s explicit direction, the extra identity was removed locally and persists through refresh/relaunch; raw sources stay available and a restore action reverses it. No provider write was made, and no student-specific identity/title/grade is hardcoded. Automatically discarding every inaccessible graded row would remove potentially valid data, so other such rows require explicit local removal.

**Precision follow-up:** [Schoology’s grade-calculation documentation](https://uc.powerschool-docs.com/en/schoology/latest/grade-calculations) distinguishes hundredth-rounded displayed item grades from unrounded values used in overall calculations. The captured account separately shows hundredth-limited reported totals and tiny reconstruction/observation mismatches; the docs do not establish an exact API precision guarantee. Inverse quarter estimates therefore propagate a conservative input-rounding budget and limit displayed decimals. Graph presentation uses same-interval observations to anchor matching reconstruction within one hundredth, without altering actual snapshots or hiding genuine small grade changes. Regressions demonstrate both the artifacts and preservation cases.

See PROJECT_STATUS.md for final build/test/device evidence. Private captures remain ignored and protected; committed fixtures are synthetic.

## Student API field availability — October 10, 2026

The October 10 original-phone installation exposed calculation issues hidden by the earlier cached-payload check: fresh student category reads omit methods/drop counts, JSON null final grades were classified as unsupported scales, and custom overall scales blocked independent numeric assignment calculations. Official [course-section field permissions](https://developers.schoology.com/api-documentation/rest-api-v1/course-section/) restrict those category fields to administrators; protected live schema diagnostics confirmed their omission in this account. This is not a provider failure. The parser restores the original points/zero-drops defaults for omitted fields, using the normal Course Grade label and preserving local editing features as requested. Reported interpretable totals remain authoritative; an overall custom-scale value is not used as a percentage. Cached agreement does not establish hidden teacher rules or future total agreement.

Current official [user grades](https://developers.schoology.com/api-documentation/rest-api-v1/user-grades/) documents per-assignment scores/timestamps and period/final totals; [grading categories](https://developers.schoology.com/api-documentation/rest-api-v1/grading-categories/) distinguishes percent and total-points methods, category weights and drop counts. Explicit unsupported category methods and incomplete contributions cannot produce a fallback grade. No provider-write endpoint is implemented.

Complete Schoology grades already include available earlier periods. The graph now reconstructs each assignment period separately across the section's year, avoiding quarter/semester rollup duplication and retaining saved observations. A new midyear connection needs no earlier local install to draw dated prefixes. This uses current scores/latest timestamps; it cannot recover overwritten score revisions or invent unavailable dates. Synthetic fresh-install regressions cover quarter and semester-only years. An actual original-phone read with zero previous sources retrieved 119 dated graded rows, 67 over 30 days old; all five current graphs built earlier points without imported history. This is original-account verification, not another-account permission evidence. The documented [submission revision API](https://developers.schoology.com/api-documentation/rest-api-v1/submissions/) returns submission metadata rather than prior grade values. The user-grade API's timestamp filter selects current rows updated since a time; it does not reconstruct older score versions. It documents include_all_enrollments for inactive grades, but accessibility of inactive sections/metadata in friends' accounts remains unverified. Current reads use enrolled sections and complete grades with no timestamp/grading-period cutoff.

The October 8 assignment audit used snapshots already saved on the student's phone; an additional fresh launch did not complete before phone access ended. October 10 installation/live refresh evidence is recorded in PROJECT_STATUS.md. Future equivalence, independent account verification and a controlled before/after speedup remain unverified.


## Authentication and endpoint references

Personal API keys use OAuth 1.0 HMAC-SHA1 with fresh nonces/timestamps and signatures for redirects. Use the enrolled section ID for accessible metadata, retaining any verified grade-owner alias for grade identity. Student keys do not establish administrator webhook authority. Complete reads, not an unverified changed-since feed, drive the app.

Official references: [authentication](https://developers.schoology.com/api-documentation/authentication/), [users](https://developers.schoology.com/api-documentation/rest-api-v1/user/), [course sections](https://developers.schoology.com/api-documentation/rest-api-v1/course-section/), [grades](https://developers.schoology.com/api-documentation/rest-api-v1/grade/), [grading categories](https://developers.schoology.com/api-documentation/rest-api-v1/grading-categories/).

## UI reference

The user's screenshots and retained SwiftUI source define the presentation: course cards, semester summaries, progression with held grade/date selection, recent assignments, collapsible categories, local scenarios and final calculator. The chart uses evenly spaced dated events and monotone interpolation, a neutral line and gradient fill. Interpolated geometry never becomes a reported grade. The PWA's refresh indicator is a spinner without instructional prompts.

Bessy's public [website](https://www.bessy.io/) describes related product features; its private algorithms were not accessed. GradeViewer uses original source and assets.
